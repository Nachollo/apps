## Evidencia funcional positiva

### Backend y reservas

`src/http-server.js` implementa endpoints reales para:

- disponibilidad;
- creación de reservas;
- listado;
- modificación;
- cancelación;
- widget público;
- chat;
- webhooks.

Las reservas se escriben mediante `store.mutate(...)`, no solo en el DOM.

### Persistencia real

`src/store.js` implementa un almacén JSON con:

- lectura al iniciar;
- serialización de mutaciones;
- escritura temporal;
- `rename` atómico;
- recuperación de fichero corrupto;
- audit log;
- deduplicación de eventos webhook.

Es una persistencia real y adecuada para piloto/local, aunque no para escalar un SaaS multiusuario.

### Seguridad de producción

`src/production-checks.js` exige en producción:

- `ADMIN_API_KEY` de longitud mínima;
- `CORS_ORIGINS`;
- HTTPS;
- secreto de webhook Telegram si se activa;
- configuración completa y firma de WhatsApp.

Se comprobó de forma independiente:

```
NODE_ENV=production node server.js
```

sin configuración de producción.

El servidor **rechazó el arranque** con exit code 1 por:

- ausencia de `ADMIN_API_KEY`;
- ausencia de CORS;
- `PUBLIC_BASE_URL` sin HTTPS.

Esto acredita que el modo inseguro de desarrollo no se acepta silenciosamente como producción.

### Integraciones de canales

Existe código real para:

- configuración de webhook Telegram;
- validación de secreto de Telegram;
- validación de firma `x-hub-signature-256` de WhatsApp;
- configuración de Meta Graph API.

No se han probado conexiones reales porque no se han proporcionado credenciales.

### IA

`src/services/ai.js` implementa una integración real con:

`POST https://api.openai.com/v1/responses`

y usa:

- instrucciones por agente;
- conocimiento aprobado;
- historial reciente;
- `store: false`;
- timeout;
- fallback controlado.

Sin `OPENAI_API_KEY`, o si OpenAI falla, devuelve un motor heurístico local claramente etiquetado como `local-demo` / `local-fallback`.

## Limitaciones verificadas

### 1. No está en modo producción

El healthcheck actual devuelve `mode: local-demo`.

No están configurados:

- clave administrativa;
- firma WhatsApp;
- secreto Telegram.

Esto es correcto para la prueba local, pero impide afirmar que exista un despliegue productivo operativo.

### 2. Persistencia JSON

El propio diseño usa `data/store.json`.

Es suficiente para demo/piloto de baja concurrencia, pero no sustituye PostgreSQL, migraciones, aislamiento multi-tenant, backups y control transaccional para un SaaS comercial.

### 3. IA local no es un LLM

El modo sin OpenAI es un motor heurístico basado en expresiones y respuestas prefijadas. Es útil como degradación, pero no debe denominarse IA local equivalente a un LLM.

### 4. Ollama no está implementado en el código revisado

No se localizó integración Ollama en V4.1. La ruta implementada es OpenAI Responses API + fallback heurístico local.

### 5. Canales externos no probados end-to-end

Telegram y WhatsApp tienen código y controles de seguridad, pero no se han ejecutado contra cuentas/credenciales reales.

### 6. No hay evidencia todavía de pagos, facturación o provisioning SaaS completo

El núcleo de reservas/agentes/widget está implementado. Para comercializarlo como SaaS faltaría acreditar, según el alcance que se quiera vender:

- alta/autenticación de clientes;
- aislamiento real por tenant;
- facturación/pagos;
- gestión de planes;
- observabilidad;
- backups;
- despliegue;
- colas/reintentos de webhooks;
- SLAs y recuperación.

## Conclusión

**ReservIA V4.1 ya no debe clasificarse como una demo visual.** Existe un piloto funcional reproducible: servidor real, persistencia, API, seguridad de producción, widget y tests 10/10.

El veredicto correcto es **FUNCIONAL PARCIAL / PILOTO FUNCIONAL PROBADO**. La distancia hasta producción ya no está en “hacer que funcione”, sino principalmente en infraestructura SaaS, persistencia multi-tenant, credenciales/integraciones reales, autenticación comercial y operación.
